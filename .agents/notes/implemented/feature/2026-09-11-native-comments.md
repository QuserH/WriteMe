# Agent Note: 原生段落评论、逐条回复与文字批注

Status: implemented

## Problem

用户要求查看实际 Craft 的段落评论，随后明确要求 QQ 空间/帖子式的评论：每段都能发起留言，每条消息都能回复，回复也能继续被回复，不需要已解决/未解决状态。仅提供文档级输入框或选区批注不能满足这条路径；父消息关系还必须在编辑、删除、撤销、保存和同步后保持。

2026-09-12 用户进一步要求删除后直接消失，不显示“评论已删除”占位。该规则同时适用于消息列表、回复引用和同步冲突预览；不能因隐藏消息而连带丢掉后续回复，也不能在分页中留下空名额。

## Decision

### 段落入口与帖子式回复

- `BlockEditor.ParagraphComments.cs` 为有评论的段落提供段下摘要：小头像、未删除消息数和相对时间；没有评论的段落在悬停时显示右侧入口。空段落、标题、折叠标题、列表、代码、表格/分栏内的段落均可直接评论，整体复合块也可作为目标，无需文字选区。正文预留 38px 侧边点击空间，紧凑区域预留 24px；仅实例化可见行的按钮。
- `BlockTextFormatter` 只在块的最后一个排版行之后追加 28px 页脚，按钮与下一段不重叠。AvaloniaEdit 会将短文字行在 `DefaultLineHeight` 内居中，适配器先保留原行盒与居中偏移，再追加页脚；绘制、基线和选区矩形同步，不能只增加 `TextLine.Height`。原文字、断行、光标和输入法坐标保持，移除评论/撤销恢复原高度。拖动预览携带只读评论目录，复用页脚与源区域宽度。
- 单击气泡或块菜单“添加段落评论”打开对应段落附近的原生浮层；`Ctrl+Alt+M` 对当前段落发起评论，有选区时创建文字批注，标题焦点下创建文档评论。实际 Craft 参考确认了段落操作栏/更多菜单入口及段下输入框；回复关系按用户指定的帖子逻辑实现。
- `CommentsPane.cs` 同时承担段落浮层与全文评论侧栏，复用一份草稿和操作逻辑。段落浮层只展示该段的评论与批注，采用实际 Craft 弹层测得的 352px 内容宽度，窄视口按可用空间收缩，首选高度范围为 104–500px；按实际内容高度和可见空间定位，表格/分栏浮层位于根窗口区域，不受单元格裁剪。“全文”转到 324px 右栏。关闭浮层、点击外部或滚离目标保留草稿；中文预编辑期间不能误发送、关闭或切换目标。
- 每条可见消息都有“回复”入口。回复显示作者、父消息摘要和正文，点击父摘要定位原消息；头像与文字悬挂对齐，回复共用一条浅色竖线和固定缩进，深层关系由父消息链接表达，不无限压窄正文。头像取作者首个 Unicode 字素，不硬编码“我”。移除重复的蓝色卡片边框，消息菜单在悬停/键盘焦点时显现；输入框明确显示回复对象。“写评论”在同一段新建独立评论，取消回复回到段落评论草稿。Enter 换行，Ctrl+Enter 发送。
- 就近浮层中的整段评论不重复显示整段引用，文字批注与全文评论仍显示原文摘要。空的新评论输入框保持紧凑，有输入后再显示发送栏与快捷键提示；回复对象和编辑状态始终明确。面板使用中性表面与细分隔线，颜色随主题更新，不改变讨论与删除语义。
- 不提供解决状态、解决按钮或状态筛选。评论气泡及全文入口计数为未删除的评论和回复数。

### 文档契约与父消息关系

- `NoteComments.cs` 在根 `attrs.writemeComments` 保存版本 1 的讨论目录。每个 `CommentThread` 有稳定 ID、引用摘要、是否锚定及 `wholeBlock`，包含有序 `CommentMessage` 数组；消息保存 ID、作者、正文、创建/编辑时间、`replyTo` 与 `deleted`。首条消息没有父消息，其余回复指向同一讨论中先存在的消息；旧平铺回复缺省指向首条评论。校验拒绝跨讨论父 ID、前向引用、自引用、重复 ID 和非法墓碑，因而不能构成循环。
- 删除首条评论意味着删除这条评论及全部回复，界面先就地确认。删除单条回复将其正文清空并置 `deleted`，内部保留 ID/父关系和后续回复；渲染前过滤删除项，不保留头像、时间、空位或删除提示，后续消息也隐藏指向删除项的引用按钮。其他消息不被连带删除，仍可继续回复。删除均可立即撤销，也进入正文统一历史；恢复后消息及原引用重新显示。
- 整段评论 ID 保存在目标节点 `attrs.writemeCommentIds`；文字范围使用 `comment` mark 的 `attrs.ids` 数组。运行期节点 GUID 不落盘，稳定讨论 ID 随 JSON 属性/富文本片段一起携带。多个文字批注可重叠，一段可以有多条独立评论。
- 评论经 `DocumentSession` 的根历史提交，不增加独立评论 SQLite 表或撤销栈；单元格与栏通过 `HistoryOwner` 写根目录。回复/修改/删除核对完整预期讨论快照，旧窗口或旧按钮不能修改另一篇文档，也不能覆盖后来出现的回复。相同内容的修改和重复删除为无操作。
- 单篇最多 1,000 条讨论、10,000 条消息（含内部删除标记），每条消息最多 20,000 个 UTF-16 单位，引用摘要最多 2,000；仍受既有文档/同步大小限制。未知目录版本原样保留并禁止评论写入，严格导入拒绝当前版本的损坏结构。

### 关联、草稿与编辑边界

- 整段改字、清空或转换样式保留段落评论；结构拖动随目标节点移动。Enter 拆分时评论留在原段，合并文字时承接仍有内容保留的末段评论；真正删除的段落保留讨论及旧引用，显示原文已删除。撤销恢复关联。表格整格清空/TSV 替换保留首段身份及段落评论，被替换的文字批注失效。
- 文字批注随富文本移动/拆分，清除格式、转换为代码块不丢失其结构标记。只有在批注内部插入的文字才继承关联，两端插入和整段替换不扩大或复活旧范围。复制块剥离所有评论关联；复制整篇文档保留完整目录与关系。
- 评论草稿按文档和新评论/回复目标/编辑目标保留在内存。重新打开段落恢复最近的对应草稿，回复的回复不会被重定向到首条评论。进程退出后不恢复未发送草稿。
- 新评论草稿捕获块 ID、路径和根 JSON 签名。当前会话中段落草稿跟随改字/移动，文字批注草稿要求原块文字未变；重开文档只有相同序列化签名才允许按路径重新绑定。目标删除或版本不符时保留文字并提示，不能猜测重复文字来重新挂接；可以显式改为文档评论。

### 保存、同步与渲染规模

- 不可变根的评论索引使用弱引用缓存，段落浮层按根/目标缓存解析，滚动只更新可见气泡和坐标。全文每批显示 30 条评论；展开项显示首条及最近 20 条未删除回复，可手动加载更早消息。定位不在当前批次的父消息只额外显示该条，并从剩余数量扣除；删除项不占名额，全部回复删除后不显示“查看 0 条回复”。
- SQLite、自动保存、本地版本、JSON 和 ZIP 原样携带目录、锚点、回复父 ID 及内部删除标记。同步冲突摘要只显示未删除消息，且隐藏失效父引用。Markdown/纯文本仅导出正文，连自定义 JSON 围栏中的评论标记也剥离；导出提示说明完整评论应使用 JSON/ZIP。见 [页面与可携带性](2026-09-10-page-assets-and-portability.md)。
- 个人 [M6 同步协议](../architecture/2026-09-08-sync-docker-crdt.md) 传送整篇文档中的评论。应用同步等待评论输入法预编辑结束，冲突预览显示消息和回复对象，评论并发不会被当作“正文无变化”忽略。本机作者默认“我”；[共享工作区](../architecture/2026-09-12-shared-workspaces-and-realtime.md) 另使用稳定账号身份与逐条消息 CRDT，`CommentsPane` 的可选头像和作者显示工厂读取当前成员资料，不改变个人资料库的存储契约。

- 2026-09-12 删除显示调整通过 39 项评论/持久化/共享副本/真实 HTTP 与 WebSocket 数据回归，包含删除后摘要过滤、后续父关系、JSON 往返与撤销恢复。按用户要求，本轮不执行原生或网页 UI 验收；已有交互脚本同步调整删除、引用和分页断言。
- `CommentInteractionTests.cs` 使用真实 Avalonia headless 指针/键盘完成段落和块菜单入口、逐条回复及回复的回复、父消息定位、编辑/删除/撤销、草稿/IME/文档切换保护、单元格/分栏浮层与有界消息显示；新增普通/大行距下段落页脚高度、原基线/光标、下一段位置和撤销恢复的几何回归。渲染检查覆盖浅色、深色和 820×560 窗口。
- `CommentPersistenceTests.cs` 的 2 项回归通过 SQLite 重新打开、本地版本、JSON、ZIP、整篇副本、回收站及真实 HTTP 双库同步，验证段落锚点和深层回复父 ID；只改评论时的双版本冲突也保留并展示差异。
- 本机评论、共享身份与段下摘要渲染产物位于 `artifacts/native/qa-mobile-accounts/`，不进入 Git；整套回归与发布验证记录在共享架构笔记。

## Alternatives considered

- **不增加模型，复用文档评论/文字选区**：实现和交互最少；不能评论空段落，也无法区分改字与删除整段，用户明确要求每段有自己的讨论。
- **平铺回复加已解决/未解决状态**：适合审阅待办，状态筛选能清理长讨论；用户明确需要帖子式留言且不需要处理状态，因此去掉该流程，用稳定父消息 ID 支持回复的回复。
- **独立 SQLite 评论表和独立同步实体**：适合多人共享、按条权限与并发回复；当前同步是账号隔离的整篇文档协议，会额外引入跨实体引用、删除和恢复顺序。沿同一文档事务实现，共享协作需要另行设计协议。
- **只保存块路径与文字偏移**：不需要正文标记；移动、拆分或插入前文后容易指错，重复文字无法可靠找回。整段与文字范围分别携带稳定讨论 ID，摘要只用于显示，不自动猜测新位置。
- **删除回复时删除其整个子树**：没有墓碑，存储与渲染更简单；却会连带删除后续消息，破坏帖子上下文。保留内部删除标记以维持关系，代价是目录仍占用一个消息名额。
- **复用原有可见删除占位**：能解释回复链中缺失的父消息，且无需修改分页；用户明确要求删除后消失，因此只在内部保留父关系，所有展示路径过滤删除项，撤销再恢复引用。
- **每层回复都套独立卡片与边框**：父子关系可直接由框线表达，也便于强调选中项；在 352px 浮层中层层边框挤占文字宽度，重复引用也使空评论显得冗长。使用固定回复缩进与显式父消息引用，保留深层关系而减少视觉分隔。
- **只在右侧悬浮计数，或插入真实空行腾位置**：前者不影响排版，后者不用接入文字度量；用户要求段落下方的 Craft 入口，悬浮无法稳定对齐，真实空行又污染正文和历史。使用展示页脚，但必须随固定排版包维护行盒、命中和选区回归。

## Consequences

- 收益：段落拥有独立的帖子式讨论，消息的回复对象清楚；删除中间回复不清空后续内容，编辑、历史、保存和携带仍走现有文档事务。
- 代价：正文属性与文字 marks 增加结构关联，转换、复制、整格替换和导出必须维护区别；草稿只在进程内保留，内部删除标记仍计入上限，界面不展示这些标记。
- 边界：个人 M6 的文档级同步仍可能要求选择并发版本；跨账号实时回复只在独立共享工作区中提供。@提醒、消息通知和其余 Craft 功能不能由评论功能推定完成。
